# ALLinSSL 群晖证书部署插件

[ALLinSSL](https://github.com/allinssl/allinssl) 的模块插件。启用后，工作流中会多出一个 **「部署到群晖」** 节点，把申请或上传的 SSL 证书自动导入群晖设备的证书管理。

- 支持群晖 NAS（DSM）和群晖路由器（SRM），两者使用同一套接口
- 续期后原位替换设备上的证书，保留它的默认状态和各服务的绑定；同一张证书不会重复上传
- 可选择将证书设为设备的默认证书

## 环境要求

| 项目 | 要求 |
| --- | --- |
| ALLinSSL | v1.1.4 及以上（带「插件管理」页面的版本） |
| 运行平台 | Linux amd64 / arm64 |
| 群晖账号 | 属于管理员组，且 **未开启两步验证** |

> 本仓库 1.x 版本是旧式的「部署插件」（单个可执行文件 `synology_dsm` / `synology_srm`）。2.0.0 起改为模块插件，两者安装和使用方式不同，迁移方法见 [从 1.x 迁移](#从-1x-迁移)。

## 安装

### 1. 下载

打开本仓库的 [Releases 页面](https://github.com/synologyer/allinssl_plugins/releases/latest)，下载与运行 ALLinSSL 的机器处理器对应的压缩包：

| 处理器 | 下载 |
| --- | --- |
| Intel / AMD（`uname -m` 显示 `x86_64`） | `synology_<版本>_linux_amd64.zip` |
| ARM（`uname -m` 显示 `aarch64`） | `synology_<版本>_linux_arm64.zip` |

同时提供内容相同的 `.tar.gz`，习惯用命令行的可以下载它。

### 2. 放入 ALLinSSL 插件目录

解压得到 `synology` 文件夹，把它整个复制到 ALLinSSL 的插件目录（默认是 ALLinSSL 运行目录下的 `plugins`）。用 Docker 运行时，复制到映射出来的插件目录即可，例如群晖上的 `/volume2/docker/allinssl/plugins/`。

复制后的结构必须如下，**文件夹名必须是 `synology`**，不能改名：

```text
plugins/
└── synology/
    ├── plugin.json          # 插件清单
    ├── bin/synology         # 后端程序
    └── frontend/index.js    # 节点配置表单
```

### 3. 启用插件

1. 登录 ALLinSSL，打开 **插件管理**
2. 找到「群晖证书部署」，点击 **启用**，运行状态应变为「运行中」
3. 按提示 **刷新页面**，工作流中才会出现新节点

## 使用

1. 打开 **自动化部署**，新建或编辑一个工作流
2. 先添加 **申请证书**（或 **上传证书**）节点
3. 在其后点击加号，选择 **部署到群晖**
4. 点击该节点，填写配置并保存：

| 配置项 | 说明 |
| --- | --- |
| 证书来源 | 使用哪个节点产出的证书，默认选中最近的申请/上传节点 |
| 设备地址 | 以 `http://` 或 `https://` 开头，例如 `https://192.168.1.2:5001` 或 `https://nas.example.com`。不写端口时使用默认端口（http 为 80，https 为 443）；直连设备时 DSM 一般是 5001，SRM 是 8001 |
| 用户名 | 群晖管理员账号 |
| 密码 | 该账号的密码 |
| 证书描述 | 证书在群晖中显示的描述，留空则为 `allinssl-` 加证书的第一个域名。插件按这个描述找到上一次上传的证书并原位替换 |
| 设为默认证书 | 开启后，证书会成为设备的默认证书，并在上传后确认是否生效。关闭时保持群晖里原有的设置。默认关闭 |
| 重复部署 | 与内置部署节点的同名选项一致：与上次部署的证书相同且上次部署成功时跳过，不连接设备。选择「不跳过」时每次执行都重新上传并原位替换。默认跳过 |
| 跳过证书校验 | 不校验设备自身的 HTTPS 证书。设备使用自签名证书或通过 IP 访问时需要开启。默认开启 |

5. 保存工作流并执行

需要部署到多台设备时，添加多个「部署到群晖」节点即可。

### 部署行为

做法与 acme.sh 的群晖部署脚本一致：不是每次新建一条证书，而是替换设备上已有的那一条。

- **按描述查找**：在设备的证书列表里找描述与「证书描述」相同的证书
- **找到则原位替换**：沿用原证书的 ID 上传新证书。原证书是默认证书的，替换后仍是默认证书；各服务（DSM 界面、反向代理、WebDAV 等）与它的绑定也都保留。群晖会自行重新加载用到这张证书的网页服务，不需要手动重启 nginx
- **找不到则新建**：第一次部署时新建一条证书。想让它被使用，开启「设为默认证书」，或在群晖「控制面板 → 安全性 → 证书 → 设置」里把服务指给它；之后的续期都会原位替换，无需再设置
- **重复部署**：选项为「跳过」时，本节点上次成功部署的就是这张证书则直接跳过；没有部署记录时再和设备上的证书比较（域名和过期时间都相同即视为同一张）。跳过后，后面的通知节点如果也开启了「跳过」选项，就不会重复发送通知。修改了设备地址、证书描述或「设为默认证书」后会重新部署一次
- **设为默认证书**：开启后，上传完成会重新读取证书列表确认；没有生效时再单独设置一次，仍不成功则节点报错
- **证书不在有效期内**：直接报错，不上传

从 2.0.x 升级：旧版本每次续期都会新建一条描述为 `allinssl-` 加 6 位字符的证书。新版本第一次部署时会接管其中域名一致的一条（优先默认证书，其次最晚过期的），替换它并把描述改为新的写法；其余旧记录不会自动删除，可以在群晖里手动清理。

### 注意事项

- 节点配置（包括密码）随工作流保存在 ALLinSSL 的数据库中，建议为部署单独建立一个群晖管理员账号
- 工作流日志里不会显示本节点失败的具体原因。插件把每次部署的结果和失败原因写在 ALLinSSL 数据目录下的 `data/plugins/synology/synology.log`（同目录的 `deployed.json` 是各节点上次成功部署的记录，删除它会让下次执行重新部署），同样的内容也会输出到 ALLinSSL 进程（容器）的日志中，以 `[synology]` 开头

## 升级

1. 在 **插件管理** 中 **停用** 插件
2. 用新版本覆盖 `plugins/synology/` 目录
3. 重新 **启用** 并刷新页面

`plugin.json` 发生变化（例如版本号）时必须先停用再启用，直接重启会提示「模块清单已变化」。已保存的工作流节点配置不受影响。

## 从 1.x 迁移

1. 按上面的步骤安装并启用 2.x
2. 在工作流中，把原来「部署」节点里选择 `synology_dsm` / `synology_srm` 插件的那一步，换成新的「部署到群晖」节点，并重新填写设备地址、用户名和密码
3. 确认新节点工作正常后，删除插件目录下旧的 `synology_dsm`、`synology_srm` 可执行文件，以及授权 API 管理中对应的旧授权

## 常见问题

**插件管理里看不到插件**
检查目录结构是否为 `plugins/synology/plugin.json`，以及目录名是否为 `synology`。

**运行状态为「清单无效」或「运行异常」**
查看「最近错误」一列。常见原因：`bin/synology` 没有执行权限（执行 `chmod +x plugins/synology/bin/synology`），或下载了与服务器架构不符的包。

**启用后工作流里没有「部署到群晖」节点**
启用或停用插件后需要刷新页面。

**工作流执行失败，但日志里看不到原因**
打开 ALLinSSL 数据目录下的 `data/plugins/synology/synology.log`，里面有每次部署的结果和完整的失败原因。

**登录失败（错误码 400 / 403）**
400 为用户名或密码错误；403 表示账号开启了两步验证，请改用未开启两步验证的管理员账号。

**提示「没有可部署的证书」**
节点之前没有申请证书或上传证书节点，或「证书来源」未选择。

**提示 x509 / certificate 相关错误**
设备使用自签名证书，请开启「跳过证书校验」。

## 开发

```text
cmd/synology/        后端程序入口
internal/module/     ALLinSSL 模块协议（协议 1）的插件端实现
internal/workflow/   「部署到群晖」节点：读取节点配置和证书
internal/synology/   群晖 Web API 客户端与证书导入
internal/certutil/   证书解析工具
internal/testcert/   测试用自签名证书
package/             随插件发布的清单和前端入口
```

需要 Go 1.25 及以上和 make。

```bash
make help      # 显示可用命令
make build     # 生成 dist/synology（当前系统和架构）
make package   # 生成各平台发布包
make test      # 运行单元测试
make vet       # 静态检查
make fmt       # 格式化代码
```

每次推送到 `main`，GitHub Actions 会自动测试、打包并把压缩包发布到 Releases 页面。发布新版本时，修改 `package/plugin.json` 中的 `version` 再推送即可；版本号不变时，只更新该版本下的压缩包。

### 工作原理

ALLinSSL 启动 `bin/synology` 并通过环境变量下发凭据；后端程序监听本机回环端口，把地址写到标准输出。之后：

- ALLinSSL 请求 `GET /api/workflow`，得到插件注册的节点 `synology_deploy`，在工作流中对应节点类型 `plugin:synology:synology_deploy`
- 工作流执行到该节点时，ALLinSSL 请求 `POST /invoke`，把节点配置和证书交给插件，插件调用群晖 Web API 完成导入
- 前端入口 `frontend/index.js` 向工作流编辑器注册节点的标题、摘要和配置表单
